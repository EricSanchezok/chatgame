# 会话优先游戏布局

## Status
Superseded by [0029](0029-reui-app-shell-and-ui-api-v5.md)
Class: feature

## Context and Problem Statement

巨幅固定场景、左右永久账簿、顶部密集读数和底部双重操作把聊天游戏呈现成工业监控台。叙事、状态和操作同时争夺注意力，首屏不能回答“发生了什么、我在哪里、现在能做什么”，并产生嵌套滚动、缩放失控与移动端不可玩等问题。

## Decision Drivers

- 对话是游戏行为、反馈与世界变化的连续时间线。
- 首屏必须让叙事、当前位置和下一步行动按单一顺序被理解。
- 常驻状态只保留会改变当前决策的少量信息。
- 详细系统按需出现，关闭后回到原阅读位置。
- 桌面、窄屏、短横屏和 200% 文字保持同一信息层级。

## Considered Options

- 继续打磨三栏控制台的比例、字体和动效。
- 把固定场景缩小，但保留左右永久面板。
- 采用会话优先主舞台，媒体进入消息流，详细系统进入临时浮层。

## Decision Outcome

默认游戏壳只有一个主滚动区：桌面正文宽度约 760–860px 的居中会话流。世界叙述使用无气泡段落；NPC 消息显示头像、姓名、职业与可访问公开资料；玩家消息为右对齐紧凑气泡；系统消息为低调结果与警告。内部事件 id、handler 名和调试日志不得进入玩家转录。

地点、事件、遭遇与关键物品由 `MediaCue` 作为消息卡插入会话。地点与事件图片使用 16:9 内容卡，不作为固定背景。顶部 56–64px 只显示剧本、位置/时间及三到四项关键资源；右上只有一条可点击目标追踪；地图、任务、背包、人物、证据等通过背景 dim + blur 的居中 Dialog 打开，手机端转为全屏。

composer 与正文同宽，先列三到五个当前建议行动及权威成本/风险预览，再提供始终可用的自由输入和唯一“发送”提交。不得并列“执行”“签署”“记入班账”等竞争性主按钮。新消息约 160ms 淡入、媒体约 360ms 展开、面板约 220ms 淡入缩放；减少动效时取消位移、缩放与非必要过渡。

宿主是安静的画布，不是另一个主题。宽屏游戏画布最大约 1180px，正文最大约 816px，超宽屏继续增加外部留白而不拉长行宽。HUD 用章节栏的文字层级与微型状态线表达，不使用全宽表格、等宽分栏或整排描边；目标追踪是正文右侧批注，工具动作并入同一轻量侧栏。系统反馈是时间线状态行，建议行动是文本选项，只有选中后才展开一行预检。Dialog 以完整资料页组织内容，避免把每个字段再包成独立卡片。

内置剧本必须证明深度个性化不依赖接管 `game-shell`：只能通过 HUD、目标追踪、消息、媒体、composer、panel、主题和本地资产形成视觉语言。媒体按用途区分地点、事件、首次相遇与物品语法；同一叙事段不得连续重复同一素材。所有中文正文使用覆盖完整的现代中文字体栈，等宽字体只服务时间、数值和测量。视觉验收除响应式和 axe 外，还必须在 2560px 与 5120px 宽屏检查信息密度、阅读行宽、漂浮工具与重复描边。

《灰烬镇》和《星港》继承这套默认壳，不注册自己的永久三栏 `game-shell` 或固定 `scene`。两者仍以主题、HUD、tracker、行动建议、消息细节和面板表达各自世界。第三方完整覆盖能力遵循 [0027](0027-session-first-ui-api-v4.md)。

## Pros and Cons of the Options

### 打磨三栏控制台

- 好：可复用已有实现。
- 坏：优化的是错误的信息架构，视觉精致也不能恢复可玩性。

### 缩小固定场景

- 好：能释放部分空间。
- 坏：仍有多个永久注意力中心和多重滚动。

### 会话优先布局

- 好：阅读、行动和反馈形成单一时间线，详细系统仍可按需深入。
- 坏：场景图不再持续占满屏幕，必须依赖高质量消息节奏建立沉浸。
