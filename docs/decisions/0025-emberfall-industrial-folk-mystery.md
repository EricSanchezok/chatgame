# 《灰烬镇》工业民俗悬疑重做

## Status
Accepted
Class: feature

## Context and Problem Statement

《灰烬镇》的实体与 schema 覆盖较广，但玩家身份、矿井、煤精、任务、证据和社会关系没有形成可持续循环；多个身份、动作、任务与秘密路径不可达。棕色几何 SVG 与通用按钮也没有表现劳动、民俗和蒸汽魔法。

## Decision Drivers

- 玩家在十五分钟内完成一次有准备、风险、带回与结算的矿井班次。
- 煤精、公共炉和证据成为可验证的世界系统。
- NPC 由职责、欠账、承诺和主动计划驱动，而不是功能位与好感阈值。
- 视觉、声音和交互来自矿镇真实材料与劳动仪式。

## Considered Options

- 保留现有内容，只补更多事件与美术。
- 改成线性矿难推理剧情。
- 重做为工业民俗悬疑与矿井轮班的系统型世界。

## Decision Outcome

玩家接管全镇唯一公用灰灯，作为矿井见证人与巡查者，在班前准备、三至八次井下行动、带回资源/证据和公开配火之间循环。炉煤在灰灯、支护、诊所、排水泵、居民炉火和公共熔炉之间守恒，每班只能结算一次；核心结论至少由实物与证词两种独立来源互证。

第八个井下行动完成后，引擎拒绝继续深入并始终保留返镇路径；灰蚀达到危险值或资源不足时也能紧急返镇，未满足炉煤与实物见证条件的班次回到班前准备。检定失败只记录尝试、风险与已支付代价，不生成物证、资源、有效证词或结论；部分成功、成功与大成功产生不同数量或风险后果。

剧本通过 UI API v6 的 `GamePresentation` 提供动态班次目标与建议行动，并注册矿层剖面、承诺账、随身物和证据来源资料；Engine Extension v2 在自身 `runtimeState` 维护灯火、灰蚀、支护、深度、炉存、矿层压力、证据来源和班次结算。地点、矿井变化、证词、证据与配火结果进入宿主消息流，剧本不注册 `game-shell`、HUD、工具栏、composer 或暂停菜单。动作选择先消费宿主的权威 preview，再用同一结构化意图通过唯一发送操作执行；界面只接受最新预检请求序号，迟到响应不能覆盖当前选择。双源结论成立前，UI 与引擎都只允许继续取证而不呈现配火动作；证据记入事实与班次运行态，不以绕过容量的方式塞入随身物。剧本 UI 不复制权威状态或自行请求服务端。

三种配火分别给出玩家可见的下一班后果，并确定性更新对应 NPC 的承诺与计划。窄屏与短横屏通过可滚动班次条保留支护、井压与炉存，同时保留叙事结果和输入入口；主操作文字满足 WCAG AA 对比度，操作目标不小于 44px。

视觉采用煤黑、石墨灰和旧纸白的矿业纪实语言，冷青灰火是唯一高辨识强调色，氧化铜只标记少量职责与证据。账簿感来自编号、批注、文字节奏和材料细节，不再来自满屏棕褐、粗边框、表格或字面化账本控件。HUD 是紧凑的“班次简报”；灯火、支护和灰蚀是读数而非仪表盘。地点、交班事件和矿井节点各用不同的本地纪实位图，禁止连续重复同一矿镇大图；图像保留少量矿物版画质感，但不使用通用暗黑奇幻滤镜。关键证人使用公开身份档案语法，后续对话退回紧凑头像与姓名。所有素材逐文件记录来源；交互图标只使用 `currentColor`，剧本界面只消费宿主 `--cg-*` 语义变量。

首个内容面固定为两种出身、四名有职责/欠账/承诺/计划的 NPC、两个派系、一个地面枢纽、三个矿点、十三个有效动作和一次十二步内可完成的班次。每个已启用动作都改变可验证的剧本状态；无结果动作、不可达路径和模板化素材不进入该内容面。

## Pros and Cons of the Options

### 补内容与换皮

- 好：改动较小。
- 坏：保留断裂循环与不可达规则，只会扩大无效内容。

### 线性推理剧情

- 好：节奏易控制。
- 坏：揭谜后失去长期玩法，违背世界型剧本定位。

### 系统型矿镇

- 好：资源、关系、调查与周期后果互相驱动，可长期游玩。
- 坏：需要更多确定性系统、平衡模拟和独特资产。

## Consequences

- 剧本内容、扩展运行态与专属 UI 形成一个可独立验证的垂直切片，平台保持通用。
- 玩家可以从资源预检看见每次行动的时间与班账代价；灯火、炉煤和支护由引擎中央扣除，叙事不能改写数量。
- 双源结论和单次配火让调查与公共资源产生同一班次内的可观察后果。
- 行动上限与危险状态不会把玩家困在井下；紧急返镇可能放弃本班结算，但保留下一班的完成路径。
- 扩展完整世界时必须延续煤守恒、独立证据来源与职责驱动 NPC；新增内容不能绕过这些边界。
