# 0058 — 通过门禁的工作单元及时本地提交

## Status

Accepted

Class: process

## Context and Problem Statement

长时间把多个已经完成且验证通过的工作单元留在工作树，会扩大意外丢失、错误覆盖和恢复困难的范围，也让后续任务难以区分自身改动与既有改动。commit 是本地、可恢复的开发检查点；push 才会把历史共享到远端。仓库需要同时保证及时建立本地检查点、提交前门禁和外部发布授权。

## Decision Drivers

- 已完成代码应尽快获得 Git 对象存储和可回滚历史的保护。
- 每个 commit 必须对应一个边界清晰、可独立验证的工作单元。
- 门禁失败或尚未完成的状态不能进入正式历史。
- 不能把用户或其他任务的未提交改动顺带纳入 commit。
- 本地防丢检查点不能自动扩大为远端发布权限。

## Considered Options

1. 只有用户逐次明确要求时才 commit 和 push。
2. 获准的修改或构建任务在工作单元完成且门禁通过后及时本地 commit，push 仍需明确授权。
3. 按固定时间间隔或每次文件修改自动 commit。

## Decision Outcome

选择方案 2。用户授权修改或构建即包含为完成且验证通过的工作单元创建本地 commit 的授权，除非用户明确要求不 commit。每个工作单元按触碰表面运行对应检查，并由 pre-commit hook 强制运行治理门禁；通过后立即提交，不继续积压已完成单元。

commit 只暂存当前获准任务的相关文件。若工作树中的重叠修改无法安全分离，或改动尚未完成、门禁失败，保持未提交并明确报告原因。评审、诊断和状态报告不产生修改授权，也不触发 commit。未经用户明确请求不得 push。

## Pros and Cons of the Options

### 方案 1：逐次请求后才 commit 和 push

- 好：每次 Git 写操作都有最窄的显式授权。
- 坏：完成的代码可能长期停留在工作树，本地防丢和回滚边界过弱。

### 方案 2：及时本地 commit，push 保持显式授权

- 好：已验证工作快速进入可恢复历史，同时保持提交边界、门禁和远端发布控制。
- 好：把本地安全检查点与对外共享明确分开。
- 坏：实现者必须准确判断工作单元边界，并在脏工作树中严格限制暂存范围。

### 方案 3：定时或逐文件自动 commit

- 好：本地数据丢失窗口最短。
- 坏：容易提交半成品、红灯状态和跨任务碎片，破坏可审查历史。
