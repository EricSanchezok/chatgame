# 游戏管理路由卸载会话上下文

## Executive summary

控制球中的存档、世界和设置动作曾直接跳转到独立管理页面，导致 `GameSession`、assistant-ui runtime 和 SSE 一起卸载；运行中导航还把“打开设置”误解成“取消行动并退出游戏”。管理页面分别维护世界和存档列表，主菜单又依赖浏览器“当前会话”指针，产品因此形成彼此不一致的游戏内外入口。问题逃过测试，是因为 E2E 把离开 `/play` 和进入 `/saves` 当作正确结果，只验证目标页面出现，没有验证会话组件身份、SSE 连续性或后台 WorldRun。持久教训是：路由层级必须表达产品上下文边界；共享能力不等于共享页面生命周期，游戏内管理必须作为持久游戏布局的子路由。

## Summary

玩家只有游戏外和游戏中两个主要上下文。世界包安装、更新、卸载、创建新游戏和跨世界切换属于游戏外；当前世界存档与本机设置在游戏中也需要使用，但不能因此销毁对话。旧控制球把主菜单、存档、世界和设置都建模为同级全页导航，`GameSession.navigate` 在存在 active run 时先弹浏览器确认并调用取消接口，连纯设置操作也改变服务端游戏状态。

独立 `/worlds` 与 `/saves` 又把同一个“世界拥有多份存档”关系拆开。主菜单额外保存当前 Session 浏览器键，使导航偏好看起来像状态权威；世界导入只有通用 replace，缺少目标 ID 校验，世界包也没有受存档引用约束的卸载入口。每个局部页面能完成自己的操作，但组合后的用户心流没有单一模型。

## Timeline

1. 沉浸会话壳删除了 sidebar 和可见 header，将管理入口放入控制球。
2. 控制球动作继续复用游戏外 `/saves`、`/worlds` 和 `/settings`，管理路由位于 `/play/:sessionId` 布局之外。
3. 为避免后台状态不明，前端在任何运行中导航前要求取消当前行动，把资源切换策略错误扩展到无状态的设置与查看操作。
4. E2E 明确断言从游戏跳到 `/saves`，组件测试 mock 掉控制球，因此两层测试都把会话卸载固化为预期。
5. 用户以“游戏外 / 游戏中”心流检查完整信息架构，确认管理能力需要复用，但会话生命周期不能复用全页导航。
6. 路由改为持久 `/play/:sessionId` 布局与嵌套管理层，游戏外资源合并成世界包工作台，旧 `/saves` 和当前会话浏览器指针一次删除。

## Root cause

实现把“一个功能只有一份代码”误解成“一个功能只能有一个全页入口”。缺少明确的产品上下文模型后，路由按资源类型平铺，而没有区分查看设置、管理当前世界和真正离开游戏三种生命周期。控制球只是链接集合，无法表达哪些动作保持会话、哪些动作切换 Session、哪些动作退出 `/play`。

测试只验证 URL 和文本，未把 React 布局持久性或 SSE 连接身份视为契约。它没有在 WorldRun 执行期间打开设置，没有从可寻址管理 URL 硬刷新，也没有确认关闭覆盖层后的焦点恢复。浏览器 current-session 键让主菜单看起来可以“继续”，进一步掩盖了世界和存档信息架构已经重复。

## Guardrails

- [决策 0052](../decisions/0052-persistent-game-context-and-world-library.md) 把游戏外世界工作台、持久游戏布局、嵌套管理路由、三动作控制球和世界包生命周期定义为同一契约。
- `GameSession` 由 `/play/:sessionId` layout 持有，`manage/saves` 与 `manage/settings` 只替换其 children；直接访问管理 URL 也必须先重建同一游戏背景。
- 世界、存档与设置分别复用 `useWorldLibrary`、`SaveList` 和 `SettingsPanel`；外部与游戏内只组合范围不同的容器，不复制 CRUD。
- Playwright 在 active WorldRun 中打开设置，等待服务端终态后关闭管理层，并验证失败消息仍由原会话呈现；另验证管理层关闭后焦点回到控制球。
- 独立 `/saves`、当前会话浏览器键和运行中导航取消路径被删除；世界卸载及目标明确更新由 API 与数据库测试覆盖。
