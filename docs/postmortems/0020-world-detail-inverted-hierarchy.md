# 世界详情的信息层级倒置

## Executive summary

世界包工作台把标题、说明、生命周期按钮、统计、内容哈希和大面积新游戏按钮全部放在存档列表之前，导致桌面首屏主要展示低频包元数据，高频的继续游戏入口被压到滚动区域下方。首次修复虽然纠正了阅读顺序，却仍让完整内容哈希占据整宽卡片，并用过宽的后代选择器误将新游戏主文案染成弱化色。实现和评审只验证了“世界与存档在同一详情页”以及操作是否可用，没有验证空间占比和控件内部的最终计算颜色。持久修复是把存档列表定义为世界详情主体，将新游戏压缩为列表工具动作，把版本与生命周期管理移到列表之后并压缩为单行元数据；Playwright 以真实存档检查空间顺序、首屏可见性、管理区高度和主文案颜色继承。

## Summary

世界工作台的资源关系正确，但详情页仍按数据模型而非用户任务排序：先解释世界包，再提供包管理，最后才出现玩家要继续的旅程。巨型世界标题、三列事实卡和全宽新游戏卡共同占据首屏，即使只有两份存档，用户也需要向下寻找已有旅程。

这个问题不是存档组件自身过小，而是它在页面流中的优先级过低。缩小存档行无法解决入口被推离首屏，继续增加详情页高度还会让更多存档更难扫描。

## Timeline

1. 世界与存档从独立页面合并成双栏世界包工作台。
2. 详情页沿用展示型落地页构图，用大标题、事实卡和全宽主按钮强调所选世界。
3. E2E 验证安装、创建、继续、改名和删除流程，没有创建多份存档后测量首屏几何。
4. 用户在真实两存档界面中确认，存档列表被世界元数据和新游戏卡压到页面下部。
5. 详情页改为紧凑世界摘要、存档标题与相邻新游戏动作、存档列表、世界包管理的顺序。
6. 用户在修复后的真实界面中发现，新游戏主文案仍呈弱化色，完整内容哈希仍拥有不必要的大块背景和留白。
7. 新游戏计数样式改用专用类，包信息改为无卡片的紧凑单行元数据。

## Root cause

设计把“所选资源详情”误解成“先完整介绍资源”。游戏外世界页的主要回访任务其实是从已有存档继续，世界说明和包维护只在安装、更新或卸载时使用。组件 DOM 顺序和视觉尺寸都没有对应任务频率，导致业务信息架构正确而页面层级错误。

首次修复还暴露出两个更细的实现缺陷：`.cg-world-saves__heading span` 把“标题旁的存档数量”错误表达为任意后代 `span`，因此命中新游戏按钮的文字容器；包管理虽已下移，事实列表仍沿用旧展示卡的背景、圆角和大内边距。测试同样按功能存在性组织，只断言按钮和标题可见。它没有为桌面首屏和视觉层级建立任务级约束，例如存档区必须位于包维护区之前、第一份存档必须无需滚动可见、世界摘要与存档区之间不能出现大面积展示卡、主操作文字必须继承按钮前景色。

## Guardrails

- [决策 0054](../decisions/0054-composer-focus-and-intrinsic-player-bubbles.md) 继承并固定存档列表是世界详情首屏主体、世界包管理位于列表之后。
- [表现层参考](../game-design/presentation.md) 固定世界详情的阅读顺序和新游戏工具位。
- `WorldDetail` 的 DOM 顺序保持为世界摘要、存档区、包管理区，不用 CSS 重排制造视觉与辅助技术阅读顺序差异。
- 存档数量使用专用类，不用后代元素类型选择器表达局部角色；主操作标签的计算颜色必须与按钮前景色一致。
- 世界包版本和内容标识使用无背景的紧凑元数据行，完整内容标识保留在 DOM 和悬停信息中，窄空间允许视觉截断。
- Playwright 使用两份真实存档测量存档区与包管理区顺序、摘要到存档区间距、管理区与元数据行高度，并要求第一份存档完整位于 1440×900 首屏内。
