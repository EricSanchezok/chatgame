# WorldHost 启动失败遗留数据库租约

## Executive summary

本地服务器缺少模型密钥时，首个 API 请求会在模型网关校验失败前打开 SQLite 并取得单实例租约；初始化异常没有关闭这个局部数据库，后续请求全部误报数据库已被另一实例占用。生产 E2E 提供完整模型配置，单元测试又直接注入宿主，因此两层门禁都没有覆盖默认宿主的失败启动路径。初始化顺序改为先完成无资源的模型配置校验、再打开数据库，并增加连续失败不得创建数据库的回归测试。

## Summary

`WorldHost.get()` 负责装配模型目录、模型网关和本地数据库。数据库构造成功后会立即持有带心跳的租约，而模型网关构造会同步校验目录引用的全部 API key。原有顺序先打开数据库再创建网关；缺少密钥时函数在宿主进入静态单例前抛错，局部数据库对象无人关闭，租约和心跳继续存在。第一次错误反映真实配置问题，第二次开始却只剩误导性的租约冲突。

## Timeline

1. SQLite 运行时把租约获取放入 `LocalDatabase` 构造过程，宿主装配仍按数据库、模型网关的顺序执行。
2. 单元测试通过 `WorldHost.setForTests()` 注入内存依赖，生产构建 E2E 注入测试模型密钥，两者均绕过缺失密钥路径。
3. 在隔离数据目录运行开发服务器并进行浏览器复核时，主菜单显示通用服务端错误。
4. 启用运行时观测后，首个失败明确指向缺少模型密钥，紧接着的请求才出现 `LocalDatabaseInUseError`，从而定位到部分初始化泄漏。
5. 宿主装配改为先校验模型配置，确认成功后才获取数据库租约；回归测试连续调用失败路径并断言数据库文件不存在。

## Root cause

组合根对象的构造顺序没有遵守“先验证、后获取资源”，也没有在后续构造器失败时释放已取得的数据库所有权。测试关注了活跃租约拒绝第二实例，却没有覆盖默认 `WorldHost.get()` 在配置错误下的清理语义；生产 E2E 的有效配置进一步掩盖了这个分支。

## Guardrails

- [决策 0041](../decisions/0041-local-sqlite-runtime.md) 明确默认宿主必须在获取数据库租约前完成模型配置校验。
- [`world-host.ts`](../../src/server/world-host.ts) 先构造模型网关，再打开唯一的有状态资源 `LocalDatabase`。
- [`world-host.test.ts`](../../src/server/__tests__/world-host.test.ts) 连续触发无效模型配置并验证没有创建数据库文件或遗留租约。
- 开发态浏览器复核使用显式测试密钥，运行时观测用于区分首因与后续症状。
