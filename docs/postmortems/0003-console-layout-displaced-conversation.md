# 控制台布局挤走聊天游戏核心

## Executive summary

两个内置剧本在 UI API v3 上各自接管完整游戏壳，把《灰烬镇》做成“固定矿景 + 双账簿 + 操作台”，把《星港》做成满屏值班台。它们在类型、规则和自动化上能通过，却让玩家无法一眼理解叙事与下一步操作。根因不是配色或间距，而是验收把“剧本能完整替换界面”误当成“完整替换就是好界面”，缺少对聊天游戏核心信息层级的硬断言。持久教训是：扩展自由不等于内置产品可以放弃共同主舞台；真实玩家路径必须验证理解成本，而不只是 slot 可达与页面可操作。

## Summary

玩家进入《灰烬镇》后同时看到七组顶部读数、左侧班次记录、中央巨幅图片、右侧承诺账、底部多组行动和两个竞争提交按钮。叙事被压进独立小滚动区，内部事件文字也暴露给玩家。虽然每块信息都有来源，整体却没有主次，宽屏截图尤其像工业监控台而不是聊天 RPG。

## Timeline

1. UI API v3 为满足“剧本近乎完整替换体验”开放 `game-shell`、`scene`、HUD、composer 和 panel slots。
2. 两个剧本的 vertical slice 分别以矿班控制台和 Shift Console 为视觉母题，直接注册自己的三栏壳。
3. 组件、规则循环、axe 和生产 E2E 分别验证可操作性，却没有对“对话是否占据主要视觉面积”和“是否只有一个主滚动区”做结构断言。
4. 宽屏设计评审偏重素材、色彩和系统信息是否齐全，没有让玩家先用首屏回答发生了什么、在哪里、能做什么。
5. 真实玩家试用后明确指出界面混乱、文字和操作不知所云，并要求回到 Manus 式居中长会话结构。

## Root cause

直接原因是内置剧本滥用完整 `game-shell` 覆盖，把世界观中的“班次台/值班台”一比一映射为整个产品布局。扩展契约只约束状态和无障碍所有权，没有约束默认玩家信息架构。

逃逸原因有三层：设计记录强调剧本差异但没有固定对话主舞台；Storybook 与 E2E 验证组件存在、点击成功和 axe 结果，却不判断阅读主次；视觉快照能发现像素变化，不能说明用户是否理解首屏。内部事件标识进入转录也说明测试更关心引擎事件发生，而不是玩家看到的语义。

## Guardrails

- [0028](../decisions/0028-conversation-first-game-layout.md) 把居中会话、唯一主滚动、消息内媒体、单一提交和临时 RPG 面板定义为默认硬契约。
- [0027](../decisions/0027-session-first-ui-api-v4.md) 增加 objective tracker、公开 NPC/任务 view-model 与确定性 item reveal，减少剧本另建信息层的动机。
- 两个内置剧本不再注册 `game-shell` 或固定 `scene`，只覆盖 HUD、tracker、composer 与内容面板。
- 结构测试断言内置剧本使用宿主壳；真实 E2E 与视觉矩阵断言对话是主要面积、composer 始终可用、地点/事件图存在于消息流且无嵌套滚动。
- Storybook 增加世界、NPC、玩家、系统四种消息、媒体卡、目标追踪、NPC 资料、行动预览和长对话状态。
- 人工视觉验收新增 2560px 与 5120px 宽屏：正文行宽、HUD 密度、tracker、composer 和工具必须仍形成同一阅读轴，禁止全宽表格、巨大空洞和漂浮按钮孤岛。
- 内置剧本的视觉验收改为“隐去剧本名仍可区分”：灰烬镇以矿业纪实、冷灰火和来源链表达，星港以民用设施、低饱和青绿和交班语法表达；两者不得靠相同卡片模板换色完成差异化。
- 地点、事件、首次相遇与物品分别使用专属媒体语法；同一段落连续重复同一素材作为回归失败处理。
