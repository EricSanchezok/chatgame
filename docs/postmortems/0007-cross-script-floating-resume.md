# 跨剧本漂浮续玩入口

## Executive summary

启动器重做后，旧的“继续上次游戏”仍作为页面右上角漂浮条存在，而且它读取的是全局最后游玩指针，不是中央卡片所展示剧本的存档。这既破坏了单一卡牌任务轴，也可能让玩家从《灰烬镇》的卡片进入另一个剧本。根因是新游戏入口迁移时只重建了 fallback 卡片，没有把续玩能力纳入 `LauncherSlotProps` 的受控模型，旧宿主分支因此留在卡片外。持久原则是：启动器上的所有动作都必须属于当前剧本，完整 launcher 覆盖所需的能力必须通过同一 UI API 契约提供。

## Summary

有存档时，页面右上角出现独立的续玩条，中央剧本卡内只有“开始新游戏”和“选择存档”。续玩条使用 `PlayerUiSettings.lastRun`，所以当前剧本与最后游玩剧本不一致时，入口的视觉归属和实际恢复目标会冲突。

## Timeline

1. 旧启动器用全局 `lastRun` 提供“继续上次游戏”。
2. AppShell 重写把封面、说明和新游戏动作收进中央卡片，但保留了旧续玩条以维持能力。
3. 视觉测试的默认场景没有验证有存档时三个入口的共同父级，也没有覆盖当前剧本与最后游玩剧本不同的情况。
4. 玩家在真实存档环境中看到右上角漂浮条并指出它应属于中央卡片和当前剧本。
5. 续玩改为从当前 `ScriptDetail.saves` 按更新时间选择最新存档，UI API v5 增加受控 `resume` 模型，旧全局指针、controller 方法、CSS 和浮层全部删除。

## Root cause

直接原因是续玩被当成全局宿主快捷方式，而新启动器的信息架构把所有玩家入口定义为当前剧本卡的组成部分。完整 launcher 覆盖缺少续玩 view-model，导致宿主只能在 slot 外自行补 UI，形成两条布局与状态路径。

逃逸原因是结构断言只检查“开始新游戏”位于卡内，没有在存在存档时断言“继续游戏”和“选择存档”共享同一操作容器；测试数据也只有单一剧本的单一自动存档，无法暴露跨剧本恢复。

## Guardrails

- `LauncherSlotProps.resume` 只提供当前剧本按 `updatedAt` 选出的最新存档、忙碌状态和恢复 capability。
- 默认 launcher 的“开始新游戏、继续游戏、选择存档”共享同一卡片操作区；不再存在 `.cg-resume-strip`。
- [布局端到端测试](../../e2e/flows/layout.spec.ts) 断言三个入口位于中央卡片，旧浮层为零引用，并用另一个当前剧本的乱序存档验证只恢复该剧本最新存档。
- 玩家设置和 controller 不再保存跨剧本全局 last-run 指针；所有续玩目标来自当前剧本的权威存档列表。
